# Localization

English is the source language; Spanish (`es`, Mexican, tú) ships alongside
it. The tooling is [duckalization](https://github.com/soska/duckalization),
set up the way Multiplano does it (`~/personal/chronicles/localization.md`).

The short version: **write English at the call site, wrap it in `__()`, and
never invent a key.**

## Adding a string

```tsx
import { __ } from '@/i18n';

__('Log in'); // plain
__('Switched to {name}.', { name }); // interpolated
__('Charge', { context: 'verb: charge a card' }); // homonym
__({ one: '{count} card', other: '{count} cards' }, { count }); // plural
```

Then:

```bash
npm run i18n:extract    # PHP manifest + duckalize extract
npm run i18n:status     # es: N/N translated?
```

If something is missing, translate it (below), then commit the catalogs.
Run extract before `npm run test:js`: the catalog test checks what extraction
produced.

The extractor rejects template literals, dynamic messages (`__(x)`,
`__(a ? 'x' : 'y')`) and plurals without `other`. Three traps it does not
catch, which pass in English and break in Spanish:

1. **No `__()` at module scope.** It runs at import time, before the catalog
   loads. Lookup tables are functions (`lib/labels.ts`, `lib/flash.ts`, page
   `layout` functions for breadcrumbs). `module-scope.test.ts` enforces it.
2. **Placeholder values are plain strings.** Render markup around a message,
   never inside it.
3. **No sentences built from pieces.** One message per sentence.

Dates and money go through `Intl` with `activeLocale()` (`useDateFormat`,
`useMoneyFormat`), never `undefined`.

## Where a string lives

| Kind of text                                             | Lives in                                           |
| -------------------------------------------------------- | -------------------------------------------------- |
| Anything on a screen, error pages                        | TypeScript, `__()`                                 |
| Toasts                                                   | A code (`App\Enums\FlashMessage`) + `lib/flash.ts` |
| Status, type and role labels                             | `lib/labels.ts` over the generated enums           |
| Validation and ledger refusals, CSV header, offline page | PHP, `__('…')` literal                             |
| Framework messages (`validation.required`)               | `lang/es/*.php` (laravel-lang, edited to tú)       |

## Which language a request is in

`App\Http\Middleware\ResolveLocale` decides once per request:

1. `users.locale` (nullable; null means "match my browser")
2. for guests, the `locale` cookie (switcher on the public card and login pages)
3. `Accept-Language`, negotiated against `App\Support\Locales::SUPPORTED`
4. `SUPPORTED[0]` (`en`)

The browser gets `locale: { current, available, intl }` and loads that
catalog before the first paint (`bootLocale()` in `resources/js/i18n.ts`).
Changing language reloads the page. Adding a language means adding it to
`Locales` and `targetLocales` in `duckalization.config.json`, then
translating.

## One catalog, two runtimes

PHP strings go through the same catalog, brief and review as the UI:

```
php artisan i18n:manifest   app, bootstrap, views  →  resources/js/locales/php-messages.generated.ts
duckalize extract           all TS                 →  resources/js/locales/en.json + en.meta.json
duckalize translate …       en.json                →  resources/js/locales/es.json
npm run i18n:lang           es + meta              →  lang/es.json   (Laravel reads this)
```

- Only **single-quoted literals** are declared: `__('Insufficient balance.')`
  yes, `__($key)` no. Laravel keeps `:name` placeholders (TypeScript uses
  `{name}`); translations must keep them verbatim.
- `lang/es.json` is **generated**. Don't edit it; re-run `npm run i18n:lang`.
  A missing translation is left out, so Laravel shows the English.
- Sentences that Fortify or laravel/passkeys render are listed in
  `App\Support\PackageMessages` so they reach the catalog too.
- Laravel's own strings are in `lang/es/*.php`, from `laravel-lang/common`
  (dev dependency). Its Spanish says _usted_; ours says _tú_, so the files
  were edited. `php artisan lang:add` / `lang:update` undo that and also
  overwrite `lang/es.json`: re-apply the edits, then run `npm run i18n:lang`.
  `tests/Feature/Locale/I18nBridgeTest.php` fails if usted comes back.
- **New form field?** Add its Spanish name to `attributes` in
  `lang/es/validation.php`, or "El campo initial balance…" shows up in
  Spanish. The bridge test sweeps every form request and fails otherwise.

## Translating

```bash
npm run i18n:extract
npx duckalize translate brief        # → resources/js/locales/.work/es.brief.json
#   an agent (or a person) writes .work/es.out.json per the brief's instructions
npx duckalize translate apply resources/js/locales/.work/es.out.json --by <name>
npm run i18n:lang                    # regenerate lang/es.json
npx duckalize review status          # machine / approved / edited
npx duckalize review approve es --by <name>
```

The brief carries the entries, call-site excerpts, the glossary
(`resources/js/locales/glossary.json`) and the style guide
(`resources/js/locales/style/es.md`). Glossary warnings are often false
positives (a term inside another word); `doNotTranslate` errors are real.

Rewording English changes the message's id, so the old translation is
orphaned and the new text shows as untranslated. `npx duckalize translate
prune` archives orphans.

## What the gate checks

- `npm run i18n:check`: re-runs the manifest (`--check`), extract and the
  lang build (`--check`), then fails on any diff in `resources/js/locales` or
  `lang`. A new `__()` without a re-extract fails it. It compares against the
  git index, so stage or commit regenerated files.
- `npm run test:js`: `catalog.test.ts` (every message translated, no orphans,
  `{name}` and `:name` kept, plurals keep `other` and `{count}`) and
  `module-scope.test.ts`.
- `php artisan test`: `tests/Feature/Locale/` (precedence, flash codes, the
  bridge, tú, field names).
